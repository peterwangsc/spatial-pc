# Native desktop input — development validation

The desktop accepts pointer hit testing across the image and provides the system pointer style. An input-enabled host must positively negotiate SPI1 over the existing mutually authenticated TLS session; absent or unsupported input capabilities remain view-only. A click in the desktop starts control and sends a positioned button event. Hover alone cannot start control.

The client sends fixed 24-byte, increasing-sequence records for normalized position, positioned buttons, wheel units, physical keyboard HID usages, start, stop and heartbeat. It uses a bounded 128-event queue, coalesces only adjacent pointer movements, preserves event barriers, and sends at most two records per 1/120 second. A stop replaces queued events and releases host-held state. The host must independently enforce the negotiated lease, authentication, rate and input bounds; the client is not a security boundary for the host.

Input is scoped to the desktop view. Back, Focus navigation, pointer exit, keyboard focus loss, inactive scene and window removal stop control. Physical HID events use the host's layout. The separately negotiated committed-text path is described below; clipboard forwarding is not implemented. Modifiers are reconciled separately. Indirect mouse and touch/pinch events share the view, with position included in button records. Actual scroll direction, pointer targeting and keyboard behavior require hardware validation.

Validation so far:

- Sixteen Swift tests pass, including golden network-order bytes, signed wheel values, coordinate bounds, invalid events/keys, queue overflow, adjacent-only movement coalescing, stop priority and positive capability negotiation, held-key limits and inferred modifier release.
- Optimized simulator, signed device, and Release simulator builds pass. A loopback-only TLS fixture serves a synthetic 1080p pattern and accepts SPI1 without accessing Windows or injecting OS input. Connection alone produced zero input events. A desktop click produced start/down/up; hardware-keyboard forwarding in Simulator produced key records and returned to zero held keys. Focus navigation produced stop while video continued and the same desktop window remained visible.
- Actual LAN integration against reviewed Windows host `8e4225d` passed TLS 1.3 negotiation, start, four heartbeats and stop: 127 video frames received, including 25 after stop, in 3.52 seconds. Host metadata confirmed six records, no expired lease and native exit code zero. This protocol probe sent no pointer, button or key events and retained no images. A separate view-only connection rejected missing-client/untrusted-host certificates and hardware-decoded 120 frames. The certificate probe now sends a valid hello and recognizes both TLS errors and EOF rejection.
- Simulator's gaze/controller emulation did not establish external-pointer hover or scroll behavior; those are not claimed as passed. Physical AVP pointer movement subsequently passed Peter's test. Scroll and the revised keyboard behavior remain pending hardware validation. The PC's separate dedicated-window tests establish native Windows injection independently of the AVP input path.

The client retains the tested NV12 stream and native-window Focus presentation. Neither the public Release configuration nor an older view-only host silently enables remote control. This development feature does not yet constitute a consumer pairing/permission flow.


## Native keyboard revision

Physical AVP testing confirmed remote pointer movement. Peter reported that, while the streamed desktop was focused, typing reached neither the PC nor the Mac; clicking a Windows text caret did not show the floating keyboard. This is the final corrected symptom, superseding an initial report that typing stayed on the Mac. Hardware keyboard delivery is not yet marked passed.

The desktop now implements UIKit `UIKeyInput`, preserving physical HID handling for shortcuts and using committed-text callbacks for system keyboard input. A keyboard icon beside Focus uses the same reveal-on-hover behavior as the corner controls. The native keyboard can be toggled independently of the Windows application; the video stream provides no knowledge of remote text fields. Keyboard display requests are explicit observable inputs to the native surface. Pointer exit releases remote held state while leaving the native text responder available for its separate keyboard window; a subsequent explicit key/text interaction can restart control. Back, navigation and scene inactivity still stop control. Events without physical key information continue through UIKit instead of being swallowed.

Committed text requires separately negotiated `input.textVersion:1`. SPI1 type 8 carries one validated Unicode scalar in the existing fixed record. Newline, tab and deletion use existing HID taps. Text batches are limited to 64 records per callback; control scalars and invalid scalars are rejected before enqueuing. No Windows keyboard layout is guessed. Autocorrection, capitalization, smart punctuation and clipboard actions are disabled for this remote surface. Diagnostics retain only key-event/text-callback counts and responder/presentation booleans, never typed content.

Simulator validation against the loopback-only synthetic TLS fixture: the native keyboard opens through the app icon and hides through the same icon; two on-screen key taps produced two type-8 records and zero duplicate HID events. A physical-key test produced one down/up pair and no committed-text duplicate. Focus entry stopped control with zero held keys/buttons while video continued. Hardware/Simulator keyboard-forwarding configuration affects keyboard presentation; this does not prove Mac Virtual Display routing or floating-keyboard behavior on the physical AVP. The Windows helper separately passed real BMP and supplementary character delivery; actual LAN and physical AVP text checks are recorded separately as they complete.

Actual LAN text integration against Windows host `18eaf71` passed: three fixed Unicode scalars arrived in the dedicated native observer as exactly four expected UTF-16 `WM_CHAR` units with four balanced Unicode down/up events and zero unexpected events. The Mac probe received 77 video frames, including 28 after stop, in 2.211 seconds over TLS 1.3. No HID keys, Return, pointer actions or image files were involved. This exercised the real Windows helper and LAN protocol, separately from the simulator UI test. The first attempt sent nothing because a foreground query in the noninteractive SSH session could not see the interactive observer. The corrected guard verified the live observer process and its fresh atomic foreground report; the observer independently checks foreground every 5 ms and closes after 60 seconds. Physical AVP keyboard routing remains pending.

Build 8 also releases the native text responder and dismisses its keyboard when input becomes unavailable. With the floating keyboard visibly open, terminating the loopback synthetic host changed input/text availability, control, responder and keyboard-presentation flags to false; visual inspection confirmed the keyboard disappeared. No Windows session was used for this disconnect regression.

## September 14 physical keyboard follow-up

Peter confirmed that build 8 receives MacBook keyboard letters and that the floating keyboard works, including spaces. Physical Space instead highlighted and then activated the local Back button; the apparent connection crash was navigation. Build 9 removes the three desktop overlay buttons from keyboard focus with `focusable(false)`, retaining button actions and accessibility labels. This targets local keyboard navigation consuming remote typing.

The loopback simulator did not reproduce the old build's Space interception: two physical Space presses produced four balanced HID records in both builds. In build 9, clicking the keyboard button still requested the native keyboard, and clicking Back still disconnected. Optimized simulator and signed device builds passed. The actual headset must establish whether this focused change resolves Space routing; it is not yet marked fixed on hardware.
